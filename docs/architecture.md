# Architecture

Moped Finance is a single-user personal finance app: an Angular client, a Node/Express API, and PostgreSQL. It's one repo with three TypeScript packages.

| Folder | What | Key tech |
|---|---|---|
| `client/` | Web UI | Angular 21, Angular Material, Vitest |
| `server/` | REST API; also serves the built client in production | Express 4, Drizzle ORM, express-session, Jest + PGlite |
| `shared/` | Types, enums, API contracts, and calendar-date and budget-stream helpers used by both | Plain TypeScript, no runtime dependencies |

The root `package.json` holds only repository-wide tooling (Prettier).

## Path aliases

| Alias | Resolves to | Used in |
|---|---|---|
| `@shared/*` | `shared/*` | client and server |
| `@server/*` | `server/src/*` | server |

Aliases are set in each package's `tsconfig.json`, and in `server/jest.config.js` for tests. The server build runs `tsc-alias` after `tsc` to rewrite them to relative paths in `dist/`. Because the server imports `../shared`, `tsc` emits to `dist/server/` and `dist/shared/`, so the entry point is `dist/server/index.js`.

## Server

```
server/
  index.ts          app setup: session, routers, static files, graceful shutdown
  src/api/<domain>/ finance endpoints, one folder per domain
  src/auth/         login/register/session, auth middleware, users
  src/health/       GET /health (database ping), used by the Docker health check
  src/csv/          CSV reading/writing and cell parsing for imports and exports
  src/data/         DatabaseClient, EntityId, entity factories, SchemaUtil, the core/finance pgSchemas
  src/routing/      OperationHandler, Result factory, request validation
  src/logging/      logger (console and/or core.logs table)
  src/utility/      DateTimeUtil, test helpers
  migrations/       SQL migrations generated by drizzle-kit (drizzle.config.ts)
  scripts/          dev database scripts: migrate, drop, seed
  seed-data/        synthetic sample data for db:seed (see its README)
```

### Request flow

Each finance domain (`accounts`, `budget`, `categories`, `institutions`, `transactions`) has the same layers:

1. **`*-routes.ts`**: defines Express routes and calls `OperationHandler.execute` with the request schemas (`{ params, query, body }`) and a callback. `execute` parses those parts with Zod, answers 400 naming the invalid fields, or passes the typed values to the callback.
2. **`*-controller.ts`**: business rules, such as returning `Result.userErrorNotFound()` when a requested resource doesn't exist. Returns an `OperationResult` built with `Result.success(...)`, `Result.userErrorNotFound(...)` and similar; never touches `res`. Imports and exports use the domain's CSV format (`transaction-csv.ts`, `balance-history-csv.ts`), built on `src/csv/`.
3. **`*-data.ts`**: Drizzle queries, mapping rows to `@shared` types. Each domain's `IFinance*Data` interface declares its own methods, typically `retrieveAll`, `retrieveSingle`, `insert`, `update` and `delete`.
4. **`*-schema.ts`**: Drizzle table definitions and `drizzle-zod` validation schemas.

`OperationHandler` logs the operation, maps the result's `OperationStatus` to an HTTP status code, sends `data` or `{ code, message, details? }`, and turns thrown errors into a 400 (constraint violations, via `DatabaseErrorUtil`) or a generic 500. Errors raised before an operation runs (malformed JSON, rejected uploads) reach `buildErrorHandler` (`src/routing/error-handler.ts`), registered last in `index.ts`, which answers in the same `{ code, message }` shape. Uploads go through `singleFileUpload` (`src/routing/upload.ts`): one file, at most 5 MB, held in memory.

Routers are wired up in `server/src/api/index.ts` under `/api/v1/<resource>`, behind `resolveUser` + `requireAuth`, which accept a browser session or a personal API token (`Authorization: Bearer mf_…`, AUTH-11); a read-only token may only `GET`. Auth is mounted separately at `/auth` (`login`, `register`, `registration`, `logout`, `me`, `password`, and `tokens` to manage API tokens), only accepts the browser session (`requireSession`), and uses a cookie session (`express-session`, stored in `core.sessions` by `connect-pg-simple`; see `src/auth/session.ts`). `helmet` sets security headers on every response (`src/routing/security-headers.ts`).

## Database

One Postgres 16 database with two schemas:

- `core`: `users`, `logs`, `sessions`, `secrets` (the generated session secret), `api_tokens` (hashes only)
- `finance`: `institutions`, `accounts`, `balance_history`, `category_groups`, `categories`, `transactions`, `budget_streams`

Each instance has one owner (AUTH-7). `core.users` exists for login, and registration closes after the first user. Finance tables have no `user_id`: every signed-in request sees all finance data. `core.logs.user_id` records who performed an operation.

### Schema and migrations

The Drizzle tables are the one definition of the schema: `server/src/**/*-schema.ts`, plus the `users` and `logs` tables in `user-data.ts` and `log-data.ts`. They declare the foreign keys, indexes, and unique and check constraints too. Enum-like columns have `CHECK` constraints built from the `@shared` enums with `SchemaUtil.isOneOf`, so adding an enum value is a schema change.

drizzle-kit compares the tables with the last snapshot in `server/migrations/meta/` and writes the difference as a new SQL file in `server/migrations/` (`npm run db:generate`). Migrations are committed and never edited once merged. CI regenerates them and fails if the output differs from what's committed, which catches a table change without a migration.

The server applies pending migrations on startup, before it listens (APP-5.8), using `DatabaseClient.migrate`. Drizzle records applied ones in `drizzle.__drizzle_migrations` and runs all pending ones in a single transaction, so a failed migration leaves the database as it was and the server exits. The test database (`TestDatabaseUtil.createMockDatabase`) applies the same migrations to PGlite.

Migrations run on startup rather than as a separate step because there's one instance and one owner: updating means pulling a new image and restarting, with nothing to run by hand. If this ever runs as more than one instance, move migrations to a one-off job so two servers don't race.

Conventions: timestamps are `TIMESTAMPTZ`; `date` columns are calendar dates with no time zone, read and written as `YYYY-MM-DD` strings (Drizzle's `mode: 'string'`) and passed through the API unchanged; money is `DECIMAL(12, 2)`. Names of institutions, category groups and categories are unique ignoring case (unique indexes on `lower(name)`), and there's one balance per account per date. `OperationHandler` turns unique and foreign-key violations into a 400 with a message from `DatabaseErrorUtil`.

## Client

```
client/src/app/
  core/       API/auth services, auth guard, DateProviderService, dialogs (modal/), notifications,
              unsaved-changes guard, demo mode
  core/loading/  viewResource, placeholders (skeletons) and the in-place load error
  core/layout/  LayoutService, the page header, profile menu and tab-title strategy
  core/list/    the responsive list (columns when wide, two-line rows when narrow)
  core/chart/   the Chart.js wrapper, its theme colours and axis labels
  finance/    one folder per screen area: accounts, budget, categories, dashboard,
              institutions, spending, transactions, common (the value-history chart, the money display)
  settings/   the Settings list and API Tokens (Institutions and Categories live in finance/)
  login/, register/
```

- Standalone components, routes in `app.routes.ts`. The shell (`app.html`) shows the navigation as a bottom bar, rail or side navigation by window size (APP-1.2). Every screen starts with `<app-page-header>` (title, breadcrumb trail, actions projected as content), and route `title`s become the tab title through `PageTitleStrategy`. Global styles and colour tokens are in `src/styles.scss`, shared SCSS partials (breakpoints) in `src/styles/`. Fonts (Roboto, Material Icons) are npm packages bundled into the build, so the app makes no third-party requests.
- All HTTP goes through `core/api.service.ts`, which prefixes `Environment.apiUrl`. It's empty, so requests go to the origin that served the app: Express in production, and the dev server in development, which forwards `/api`, `/auth` and `/health` to the API on :3000 (`client/proxy.conf.json`). No CORS is needed. `ApiService.load` fetches what a screen shows and throws on failure, for `viewResource` to show in place (APP-2.9); `get`, `post`, `put` and `delete` are actions, whose failures show a snackbar (APP-2.2).
- Build configurations (`client/angular.json`, `client/src/environments/`):
  - `development`: debug mode (fixed "today" of 2026-05-17 plus a badge), dev login prefilled.
  - `production`: default for `ng build`.
  - `demo`: no backend. `core/demo/demo.interceptor.ts` answers requests in the browser. Currently only auth works; everything else returns an empty list.

## Production shape

In production a single container runs the API and serves the built client from Express, next to a Postgres container. The Dockerfile copies Angular's `dist/moped-finance/browser/` to `server/dist/server/public/`, which Express serves as `public` next to the compiled `index.js`. In development (ts-node) the same code resolves to `server/public/`, which is gitignored and normally empty. See [deployment.md](deployment.md) for status.
