# v0.2 design: bank sync and rules

How the Bank sync and categorization milestone is built (requirements: [SYNC](requirements/bank-sync.md), ACCT-4, ACCT-7, CAT-8, CAT-9). Written 2026-11-07 from the SimpleFIN spec, before any code. Each session corrects it as the code proves it wrong; the first confirms the open points against Bridge's demo token ([To confirm](#to-confirm)).

This doc is temporary. The milestone's last item moves what stays true into [architecture.md](architecture.md) and deletes it.

## SimpleFIN in brief

Sources: the [protocol](https://www.simplefin.org/protocol.html) (v2, still a draft) and Bridge's [developer guide](https://beta-bridge.simplefin.org/info/developers).

- **Claiming.** A setup token is a Base64-encoded claim URL. `POST` to it (empty body) returns the access URL as the response body: `https://user:password@host/path`. A claim works once; a used or unknown token gets 403.
- **Fetching.** `GET <access URL>/accounts?version=2&start-date=<unix>` with HTTP Basic auth from the URL's credentials. Other parameters: `end-date` (exclusive), `pending=1` (pending transactions, off by default), `account=<id>` (repeatable), `balances-only=1`.
- **Response.** `errlist` (`{ code, msg, conn_id?, account_id? }`, codes `gen.*`, `con.*`, `act.*`), `connections` (`conn_id`, `name`, `org_id`, `org_url?`, `sfin_url`), `accounts` (`id`, `name`, `conn_id`, `currency`, `balance`, `available-balance?`, `balance-date`, `transactions?`, `extra?`). A transaction has `id`, `posted`, `amount`, `description`, `transacted_at?`, `pending?`, `extra?`. Amounts are numeric strings, positive for money in; timestamps are Unix seconds. v1 had an `org` object per account, `payee` and `memo` on transactions, and a plain `errors` list, which Bridge still uses for its own warnings.
- **IDs.** An account ID is unique within its connection; a transaction ID is unique within its account and never reused there. Neither is promised to be stable, and nothing says whether a pending transaction keeps its ID when it posts.
- **Bridge's limits.** About 24 requests a day, with separate allowances for all-accounts and per-account requests; going past the warning level disables the access URL. At most 90 days between `start-date` and `end-date`. History depth varies by bank. Bridge updates from banks about daily. 403 (revoked or wrong credentials) and 402 (payment required) are failures the user has to fix.

## Configuration

- **`ENCRYPTION_KEY`**: 32 random bytes, Base64 (`openssl rand -base64 32`). Read and checked at startup like `LOG_RETENTION_DAYS` (`LogRetention.retentionDaysFromEnvironment`): unset means bank sync is unavailable (SYNC-1.2); set but not 32 bytes stops the server, naming the variable. Not tied to bank sync by name, so later credentials (a property-data API key for Real estate values) use it too. Goes in `.env.example`, both compose files and `deployment.md`.
- **Encryption**: AES-256-GCM via `node:crypto`, a random 12-byte IV per value, stored as `v1.<iv>.<tag>.<ciphertext>` (Base64url) so the format can change later. A small `SecretBox` in `server/src/utility/` with `seal` and `open`; `open` failing (wrong key, tampering) is SYNC-1.3's "can't be decrypted". It protects backups and database dumps, not a compromised host, which has the key too.
- **Time zone**: transaction and balance dates come from Unix timestamps through the server's `TZ` (APP-5.6), with a `DateTimeUtil` helper turning an instant into a `CalendarDate`.

## Data model

### A `simplefin` schema that finance doesn't know about

Everything bank sync stores lives in a third Postgres schema, `simplefin` (a `pgSchema` next to `core` and `finance` in `database-schemas.ts`), and its foreign keys point only one way: from `simplefin` into `finance`, never back. The finance tables get no SimpleFIN columns. So:

- Disconnecting (SYNC-1.4) empties the `simplefin` schema and leaves the user's own data as it was.
- The tables are named after SimpleFIN's own model (connections, accounts, transactions), because that's what they hold. A second provider would have a different model and get its own schema; nothing in `finance` would change.
- `finance.accounts.is_manual` is dropped. Connected (ACCT-4.3) means a `simplefin.accounts` row's `linked_account_id` is that account, which the account queries read with a join.

IDs come from `EntityId`, as everywhere else; SimpleFIN's own IDs are unique columns beside them.

| Table | What | Foreign keys into `finance` |
|---|---|---|
| `simplefin.access` | At most one row: `access_url` (sealed), `claimed_at`, `schedule_minute` (0 to 359, SYNC-3.1), `paused_reason` (null, `refused`, `undecryptable`; SYNC-1.3). | None |
| `simplefin.connections` | One row per SimpleFIN connection: `conn_id` (unique), `name`, `org_id`, `org_url`, `last_seen_at`. | None |
| `simplefin.accounts` | One row per SimpleFIN account: `connection_id`, `simplefin_id` (unique with `connection_id`), `name`, `currency`, `balance`, `balance_date`, `available_balance`, `last_seen_at` (SYNC-2.9), `is_ignored` (Don't sync), `sync_from` (SYNC-2.4). Linked is `linked_account_id` set; Not set up is neither linked nor ignored. | `linked_account_id` → `accounts`, unique (SYNC-2.5), `ON DELETE SET NULL` (SYNC-2.8) |
| `simplefin.transactions` | One row per bank transaction sync has seen: `simplefin_account_id` (cascade), `simplefin_id` (unique with `simplefin_account_id`), and the bank's `date`, `amount` and `description` as last seen. | `transaction_id` → `transactions`, unique, `ON DELETE SET NULL` |
| `simplefin.sync_runs` | One row per sync: `trigger` (`scheduled`, `manual`, `connect`), `started_at`, `requested_at` (set just before the request goes out, so a crash still counts it), `finished_at`, `status` (`running`, `succeeded`, `failed`, `skipped`), counts (accounts updated, transactions added and updated), `errors` (jsonb: Bridge's `errlist` and `errors`, and our own failure), `response` (jsonb, the parsed payload). | None |

What `simplefin.transactions` does:

- **Recognizes transactions already added** (SYNC-4.1) by `(simplefin_account_id, simplefin_id)`, without an external ID on `finance.transactions`.
- **Notices bank corrections** (SYNC-4.4) by comparing the bank's new date, amount and description with the ones it last saw, not with the transaction, whose fields the user may have edited after unlinking.
- **Remembers deletions.** Deleting a synced transaction leaves its row with `transaction_id` null, meaning "seen and deleted", so sync never adds it again (TXN-2.12).
- **Marks a transaction as synced**: one that a row points at. TXN-2.12's read-only fields apply to it while its account is connected.
- A split keeps the mapping on the transaction that became its first part (TXN-4.1); sync leaves splits alone (SYNC-4.4).

Unlinking (SYNC-2.7) only clears `linked_account_id`, so the transaction rows stay and linking the same bank account again adds nothing twice. Disconnecting deletes them all; linking after connecting again can't recognize old transactions, but SYNC-2.4's default **Sync transactions from** date starts after them.

Other changes: `core.settings` gains `bankSyncAutomatic` (boolean, default true, SYNC-3.1) and `categorizationLearning` (default false, CAT-9.1). `DatabaseErrorUtil` gets messages for SYNC-2.5's unique keys. `drizzle.config.ts` already reads every `src/api/**/*-schema.ts`; `TestDatabaseUtil` needs to clear the new schema's tables.

`sync_runs.response` keeps the latest successful payload, for SYNC-2.10, and prunes the others after 30 days on the log-retention timer. It holds what the database already holds, so it adds no new exposure, and keeping it means a transform bug can be fixed and re-run without spending Bridge's allowance.

## Code layout

All in `server/src/api/bank-sync/`:

| File | Job |
|---|---|
| `simplefin-client.ts` | The only code that talks to Bridge. `ISimplefinClient` with `claim(setupToken)` and `fetchAccounts(accessUrl, startDate)`. Uses `fetch`, which refuses URLs with credentials, so it moves them into an `Authorization: Basic` header. HTTPS only (a claim URL or access URL that isn't `https:` is refused), 60-second timeout, no retries. Parses the response with Zod, accepting v1 and v2 shapes, into our own `SimplefinAccountSet` type. Never logs URLs or bodies. |
| `simplefin-schema.ts`, `simplefin-data.ts` | The tables above and their queries. |
| `sync-quota.ts` | Counts `sync_runs.requested_at` in the last 24 hours against the cap of 20 (SYNC-3.4) and says when the next slot frees. |
| `sync-runner.ts` | One sync, the pipeline below. Used by the routes and the scheduler. |
| `sync-transform.ts` | Pure functions: a SimpleFIN account's transactions to new and changed Moped transactions, the balance entry, and the backfilled history (SYNC-4.6). Most of the unit tests go here. |
| `sync-scheduler.ts` | The timer (SYNC-3.1, 3.2). |
| `bank-sync-controller.ts`, `bank-sync-routes.ts` | The API. |

Tests use a fake `ISimplefinClient` returning fixtures recorded from the demo token (v2 and v1 shaped) in `server/src/api/bank-sync/test-data/`. CI never calls Bridge.

## The sync pipeline

`SyncRunner.run(trigger)`:

1. **Lock.** `pg_try_advisory_lock` on a fixed key; if it's taken, refuse with "A sync is already running." (SYNC-3.5). The lock also holds against two servers, should there ever be more than one.
2. **Quota.** If `SyncQuota` says no, a manual sync answers 429 with the time it frees up; a scheduled one records a `skipped` run (SYNC-3.4).
3. **Decrypt** the access URL; failing sets `paused_reason = 'undecryptable'` and stops.
4. **Request.** Insert the run with `requested_at`, then `fetchAccounts` with `start-date` 89 days before now (SYNC-3.6; one day's margin under Bridge's 90). Always the full window, rather than since the last sync: it's one request either way, it picks up corrections the bank makes later (SYNC-4.4), and a newly linked account can take its history from the latest payload (SYNC-2.10). 403 or 402 sets `paused_reason = 'refused'`; any other failure fails the run and waits for the next scheduled one.
5. **Store** the parsed payload on the run.
6. **Apply**, in one database transaction (SYNC-4.8):
   - Upsert `simplefin.connections` and `simplefin.accounts` from the payload, updating names, balances and `last_seen_at`. New accounts arrive Not set up.
   - For each linked account that's open and in USD: transform its transactions (skip pending ones and any with `posted` 0; date from `transacted_at`, else `posted`; skip dates before `sync_from` or after `DateTimeUtil.latestRecordDate()`), then look each up in `simplefin.transactions`. A new one goes through the rules and learning ([below](#rules-and-learning)), is inserted in `finance.transactions` with `adjusts_balance` false, and gets its mapping row. A known one updates its mapping row; when the bank changed its date, amount or description and its transaction still exists and isn't split, those fields are updated on the transaction too (SYNC-4.4). A known one whose transaction was deleted is left alone.
   - Record the balance as a set entry on `balance-date`'s day (ACCT-4.2), through the existing balance-history code so ACCT-5.7's shifting still applies.
7. **Finish** the run with its status, counts and Bridge's messages, and release the lock.

**Linking** (SYNC-2.3, 2.4) runs step 6's per-account part against the latest stored payload for that one SimpleFIN account, in the same database transaction as the link and as turning off `adjusts_balance` on the account's existing transactions (ACCT-5.5), then backfills balances when the account had none (SYNC-4.6). It never calls Bridge.

**Connecting** (SYNC-1.1) claims the token, seals and stores the access URL with a random `schedule_minute`, then runs a sync with trigger `connect` so the bank accounts can be listed.

## Scheduling

`SyncScheduler` is built like `LogRetention`: started in `index.ts`, an unref'd timer, stopped on shutdown. The day has four slots, `schedule_minute` and every 6 hours after it, in the server's time zone. On start and after each run it sets a timer for the next slot. On start, if the last scheduled run started more than 6 hours ago (or there's been none since connecting), it runs 2 minutes after startup instead, which covers SYNC-3.2 without ever running twice for one slot. Each slot checks `bankSyncAutomatic` and that the access isn't paused.

With 4 scheduled runs, 16 of the 20 requests are left for Sync now and connecting.

## API

Under `/api/v1/bank-sync`, behind the usual auth; read-only tokens may only `GET`.

| Endpoint | What |
|---|---|
| `GET /` | Status: key configured, connected, paused reason, Automatic sync, last run, quota (`remaining`, `availableAt`). |
| `POST /connect` | `{ setupToken }`: claim, store, first sync. Also how Connect again works (SYNC-1.3), keeping links. |
| `DELETE /` | Disconnect (SYNC-1.4). |
| `GET /accounts` | SimpleFIN accounts with their connection, link and last-seen date. |
| `PUT /accounts/:id` | `{ action: 'link', accountId, syncFrom }`, `{ action: 'create', name, type, institutionId \| institutionName, isHidden }`, `{ action: 'ignore' }` or `{ action: 'unlink' }`. |
| `POST /sync` | Sync now; returns the run. 429 over the limit, 409 while one runs. |
| `GET /runs` | The last 10 runs (SYNC-3.7). |

Account Details gets the linked SimpleFIN account's ID, name and last sync with the account, for Manage Account's Bank sync section (ACCT-7.3), which links and unlinks through the same `PUT`.

## Security

- The access URL never leaves the server: not in responses, logs, errors or the run payload (the client never puts it there).
- Bridge's messages are shown as plain text (SYNC-5.2) and never mixed with ours; our own failures are logged in full and stored on the run as a short reason.
- The claim posts to a URL the owner pasted, so it's limited to `https:`; that's the only request the server makes to a user-supplied address.

## Rules and learning

In `server/src/api/rules/`, in the `finance` schema:

| Table | What |
|---|---|
| `finance.rules` | `id`, `name` (unique ignoring case), `position` (list order, CAT-8.3). |
| `finance.rule_conditions` | `rule_id` (cascade), `field` (`original_statement`, `merchant`, `amount`, `account`), `operator` (`contains`, `equals`, `greater_than`, `less_than`), `text_value`, `amount_value` (positive), `direction` (`in`, `out`), `account_id` (FK to `accounts`, `ON DELETE RESTRICT`, CAT-8.8). |
| `finance.rule_actions` | `rule_id` (cascade), `type` (`set_category`, `set_merchant`), `category_id` (FK to `categories`, `ON DELETE RESTRICT`, CAT-8.8), `text_value`. |

Conditions and actions are child rows rather than JSON so the categories and accounts they name keep foreign keys. `field`, `operator` and `type` are shared enums behind `CHECK` constraints, so a new action (tags, hiding, notes) is a new enum value, a migration and a branch in the engine, without reshaping the tables.

`transactions` gains `category_rule_id` and `merchant_rule_id` (FK to `rules`, `ON DELETE SET NULL`) and `category_source` (`user`, `rule`, `learning`, null for Uncategorized), for CAT-8.6's notes and CAT-9.2's "categorized by the user". Editing the category sets `category_source` to `user` and clears `category_rule_id`; editing the merchant clears `merchant_rule_id`. Existing categorized transactions migrate as `user`.

`RuleEngine` is pure: given a transaction's fields, the ordered rules, which fields it may set (the category if it has none; the merchant only for an import or sync, CAT-8.4) and learning's statistics, it returns the new category and merchant and why. It walks the rules in order, matching each against the transaction as changed so far, and the first rule to set each field wins (CAT-8.3). Then, if the category is still unset and learning is on, learning picks one (CAT-9.3). Text matches ignore case. It's called by transaction create, CSV import (per row, in the import's database transaction), sync and linking (in theirs), and a rule's **Apply to existing** (CAT-8.5, that rule only). Rules and learning's statistics are loaded once per import or sync. The statistics (CAT-9.2) are one `GROUP BY` query: per lower-cased merchant, or original statement when the merchant is blank, the count of user-categorized, unsplit transactions per category.

API: `/api/v1/rules` with list, create, update, delete, `PUT /order` (the full ordered list of IDs), `GET /:id/matches` (CAT-8.5's counts) and `POST /:id/apply`. The Rules screen (`/settings/rules`) is an `<app-list>` with drag to reorder, and the rule form is a full page, since a rule has any number of conditions and actions.
